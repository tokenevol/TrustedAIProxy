HOW IT WORKS

Evidence generated on the traffic path

TAP sits at the gateway's egress and verifies the model provider's TLS connection. It signs only complete protocol semantics that can be parsed deterministically.

01

Observe the interaction

The gateway routes upstream traffic through TAP using an HTTP(S) proxy. Outbound TLS still verifies hostnames and certificate chains.

02

Extract protocol semantics

Provider protocols are normalized into a stable model and ordered messages. Ambiguous, oversized, or unsupported content remains unsigned.

03

Build a deterministic payload

Canonicalize the upstream certificate fingerprint, domain, path, and messages with RFC 8785 JCS to create reproducible claims.

04

Attach the attestation

The workload key produces an Ed25519 signature and proof_ref. Attestations return in headers; the API response body stays unchanged.

VERIFY, DON’T ASSUME

From workload proof to response verification

The trust chain has two layers. Cache workload proofs for the public key or workload lifecycle; verify each API response and check for replay.

llm-conversation-text-v1 Covers plain-text request and response messages
  1. 1
    Start with the response

    Read the proof reference

    Extract X-Attestation-Proof-Ref from the API response; fetch a proof bundle if there is no valid local cache entry.

  2. 2
    Customer-initiated

    Get a workload proof with a one-time challenge

    Call /.well-known/confidential-attestation with a unique, customer-generated challenge each time.

  3. 3
    Google trust root

    Verify the OIDC token and workload policy

    Check the signature, issuer, audience, validity, image digest, project, instance, service account, hardware, and Secure Boot.

  4. 4
    Key binding

    Bind the Ed25519 key to the workload

    Recompute the public key binding nonce and confirm that the Google token's eat_nonce binds both the challenge and the public key.

  5. 5
    Every response

    Rebuild claims and verify the signature

    Normalize the request and response for the profile, apply JCS, verify Ed25519, enforce route/model policies, and check the nonce for replay.

CLEAR TRUST BOUNDARY

Clear boundaries are part of trust

A signature proves only what its profile explicitly covers. Unsigned fields cannot be inferred from the proof.

✓
NON-STREAMING

What it can prove

  • Upstream identityDomain and HTTPS leaf certificate fingerprint
  • Request detailsRequest path and actual model
  • Text integrityRoles, order, message boundaries, and text
  • Signature originAn approved Confidential Space workload
—
OUT OF PROFILE

What it cannot prove

  • Multimodal contentImages, files, audio, and tool calls
  • Model internalsReasoning and the provider's generation process
  • Business behaviorGateway billing, availability, and uncovered fields
  • Streaming response bodyThe streaming profile covers only the request and upstream metadata
!
About streaming responses

llm-request-upstream-v1 attests to the request reaching the specified upstream and its response metadata. It does not cover any SSE event or streaming body. Clients must label streaming content as unverified.
